# N — Production Integration Audit

## Current baseline
- Flutter application with Supabase backend.
- Central N dark design system and branded Android icon.
- Vertical video feed with active/preloaded controllers.
- Video publishing with cover upload and privacy controls.
- Explore/search, profile/social interactions, inbox/notifications, wallet/gifts, security, and admin foundations.

## Hardening completed in this pass
- Added an automated Flutter widget smoke test for the N design system.
- CI now runs `flutter test` after `flutter analyze`.
- Removed user-facing access to the development-only free-coin RPC.
- Removed the authenticated grant on `n_add_test_coins`; it is no longer callable by ordinary users.
- Wallet purchase packs remain visibly disabled until a real payment provider is integrated.

## Rule
No production feature should expose a development/test credit path from the client.

## Phase 20 — Backend/RLS final audit fixes
- Fixed `public_profiles` so public profile data is readable without being blocked by the owner's private `profiles` SELECT policy.
- Removed the client INSERT policy for `notifications`; interaction notifications are generated server-side by trusted database triggers/functions.
- No claim of production deployment: apply and test `supabase/schema.sql` against the real Supabase project before release.


## Phase 21 — Database final hardening
- `public_profiles` uses `security_invoker` so public profile reads respect the underlying RLS boundary.
- Client-side INSERT/UPDATE/DELETE on `notifications` is revoked; notifications are generated by trusted database triggers.
- Added `n_mark_notification_read(uuid)` as the only authenticated path for marking a notification read.
- Added creation of the `images` storage bucket required by video covers.
- Removed the obsolete client-side `grantTestCoins()` path that referenced a removed test RPC.


## Phase 24 — Public profile access correction
- Corrected `public.public_profiles` to use a non-invoker view so the app can read the intentionally public profile fields without exposing sensitive `profiles` columns.
- Granted SELECT on the safe projection to authenticated and anonymous readers.
- The base `profiles` table remains protected by its own RLS policy.
